## 一、原理：JDK / JRE / JVM 是什么关系

一句话：**JDK ⊃ JRE ⊃ JVM**。

| 名字 | 全称 | 包含什么 | 用来干嘛 |
|---|---|---|---|
| JVM | Java Virtual Machine | 类加载器、字节码执行引擎（解释器 + JIT）、垃圾回收器、运行时内存区域 | **执行字节码** |
| JRE | Java Runtime Environment | JVM + Java 核心类库（`java.lang`、`java.util`…） | **运行**别人写好的 Java 程序 |
| JDK | Java Development Kit | JRE + 开发工具（`javac`、`java`、`jar`、`javap`、`jshell`、`jstack`、`jmap`…） | **开发** Java 程序 |

**为什么要分三层？** 开发机需要编译器和调试工具，而线上服务器只需要能跑程序。把"运行"和"开发"拆开，部署时就能只装必要的部分，更小也更安全。

**一个面试加分点：** 从 JDK 9 开始 Java 模块化了，官方不再单独发布 JRE 安装包。想要精简的运行环境，用 `jlink` 按需裁剪出一个自定义运行时（Docker 镜像里常这么做）。所以"装 JRE 就够了"这句话在现代 Java 里要打个问号。

## 二、原理：字节码与跨平台

### 1. 一个 Java 程序是怎么跑起来的

```
Hello.java ──javac 编译──▶ Hello.class（字节码） ──JVM 加载──▶ 解释执行 / JIT 编译成本机机器码 ──▶ CPU 执行
   源代码                     平台无关                         这一步才和平台相关
```

- **字节码**是一种给 JVM 看的"中间指令"，不是任何真实 CPU 的机器码。
- 每个操作系统 / CPU 架构都有自己版本的 JVM（Mac ARM 一个、Windows x64 一个、Linux 一个），它们都认识同一份字节码。

所以 **"一次编写，到处运行" 中跨平台的是字节码，JVM 本身不跨平台**。这正是面试官爱挖的坑。

### 2. Java 是编译型还是解释型？

答案是 **"编译与解释并存"**：
1. 第一次编译：`javac` 把源码编译成字节码（编译）。
2. 运行时：JVM 先用解释器逐条执行字节码（解释）；发现某段代码被频繁执行（**热点代码**），就由 **JIT（即时编译器）** 把它编译成本机机器码并缓存，之后直接跑机器码。

这也是为什么"Java 是解释执行所以比 C++ 慢"不准确：热点代码最终跑的也是机器码，而且 JIT 能根据运行时信息做激进优化。代价是程序启动时有"预热"过程。（延伸了解：GraalVM 的 AOT 提前编译可以把 Java 直接编成本机可执行文件，启动更快。）

### 3. 对比一下别的语言

| | 编译产物 | 换平台要做什么 |
|---|---|---|
| C / C++ | 特定平台的机器码 | 在目标平台重新编译 |
| Java | 字节码 `.class` | 什么都不用做，装对应平台的 JVM 即可 |
| Python | 源码直接交给解释器 | 装对应平台的解释器 |

## 三、动手：安装 JDK 25

**为什么是 25？** Java 每两年出一个 LTS（长期支持）版本：8、11、17、21、25，25 是 2025 年 9 月发布的最新 LTS。企业里 8 和 17 仍很多，Spring Boot 3 起要求至少 17，新项目越来越多用 21 和 25。25 包含了 8 / 17 / 21 的全部特性（Lambda、Stream、record、虚拟线程等），面试问到的版本特性都能在它上面实际跑。万一某个项目要求 21，可以再装一个 21 并存，用 `/usr/libexec/java_home -v 21` 切换。

**选哪个发行版？** 用免费开源的 **Eclipse Temurin（Adoptium）** 就行，它是 OpenJDK 的一个构建版本。

### macOS

1. 先看芯片：苹果菜单 → 关于本机。显示 Apple M 系列选 **aarch64**，Intel 选 **x64**。
2. 二选一：
   - 官网：打开 adoptium.net，选 Temurin 25 (LTS)、macOS、对应架构，下载 `.pkg` 双击安装。
   - Homebrew：`brew install --cask temurin@25`
3. 配置 `JAVA_HOME`（Maven、IDE 等工具靠它找 JDK）：
   ```bash
   echo 'export JAVA_HOME=$(/usr/libexec/java_home -v 25)' >> ~/.zshrc
   source ~/.zshrc
   ```

### Windows

1. adoptium.net 下载 Temurin 25 的 `.msi`（x64）。
2. 安装时在功能列表里把 **Set JAVA_HOME variable** 和 **Add to PATH** 都选上。
3. 装完**新开**一个终端（旧终端不会读到新的环境变量）。

### 验证（两个系统都做）

```bash
java -version      # 应显示 openjdk version "25.0.x"
javac -version     # 应显示 javac 25.0.x
echo $JAVA_HOME    # Windows 用 echo %JAVA_HOME%
```

> **PATH 和 JAVA_HOME 有什么区别？** 你在终端敲 `java` 时，系统按 **PATH** 里列的目录逐个找这个命令；而 **JAVA_HOME** 是给其他工具（Maven、Gradle、Tomcat、IDE）看的，告诉它们"JDK 装在哪"。`javac: command not found` 基本都是 PATH 没配好。

## 四、动手：不用 IDE，手动编译运行 Hello World

先不用 IDEA，亲手走一遍"编译 → 运行"，你才真正知道 IDE 那个绿色三角按钮背后做了什么。

代码统一放在 IDEA 建好的 `~/java-learning` 项目里，每周一个包，笔记放 `..`，不要放进 `src`：

```
java-learning/
├── src/
│   └── week01/
│       └── L01_Hello.java
├── notes/
│   └── week01.md
└── .gitignore（IDEA 生成，已忽略 out/）
```

在 `../../src/week01` 下新建 `../../src/week01/L01_Hello.java`（**自己敲，别复制**）：

```java
package week01;

public class L01_Hello {
    public static void main(String[] args) {
        System.out.println("Hello, Java!");
    }
}
```

`package week01;` 表示这个类的全名是 `week01.L01_Hello`。Java 要求包名和目录一一对应，所以它必须放在 `week01` 文件夹里。

> 文件命名：类按学习顺序加 `L01_`、`L02_` 前缀（L = Lesson），方便在 IDEA 里排序。不能直接写 `01Hello`，因为 **Java 标识符（类名、变量名等）不能以数字开头**，而 public 类的类名必须和文件名一致。

然后在终端：

```bash
cd ~/java-learning/src
javac -d ../out week01/L01_Hello.java # 编译；-d 把 .class 输出到 out/，不和源码混在一起
java -cp ../out week01.L01_Hello    # 运行；-cp 告诉 JVM 去 out/ 找类，写类的全名，不要写 .class
```

### 看看字节码长什么样

```bash
javap -c -cp ../out week01.L01_Hello
```

在 JDK 25 上会看到（常量池编号 `#7`、`#13` 在不同版本上可能略有不同）：

```
Compiled from "L01_Hello.java"
public class week01.L01_Hello {
  public week01.L01_Hello();           ← 你没写构造方法，编译器自动补了一个默认的
    Code:
       0: aload_0
       1: invokespecial #1   // Method java/lang/Object."<init>":()V
       4: return

  public static void main(java.lang.String[]);
    Code:
       0: getstatic     #7   // Field java/lang/System.out:Ljava/io/PrintStream;
       3: ldc           #13  // String Hello, Java!
       5: invokevirtual #15  // Method java/io/PrintStream.println:(Ljava/lang/String;)V
       8: return
}
```

再看 class 文件的开头（Mac 自带 `xxd`）：

```bash
xxd ../out/week01/L01_Hello.class | head -1
# 00000000: cafe babe 0000 0045 ...
```

前 4 个字节是 `cafe babe`，这是所有 class 文件的"魔数"；紧接着是版本号，JDK 25 编译出来的主版本号是 **69**，所以你应该看到 `cafe babe 0000 0045`（`0x45` = 69）。对照记一下：JDK 8 = 52，17 = 61，21 = 65，25 = 69，每个大版本加 1。JVM 加载时会检查这个版本号。

### 再试一种写法

```bash
java week01/L01_Hello.java   # JDK 11+ 支持：直接运行单个源文件，在内存里编译，不生成 .class
```

### `main` 方法为什么长这样

- `public`：JVM 要从类外部调用它。
- `static`：JVM 启动时还没有任何对象，静态方法不需要先 `new` 对象就能调用。
- `void`：程序退出码由 `System.exit()` 决定，不靠返回值。
- `String[] args`：接收命令行参数，`java -cp ../out week01.L01_Hello a b` 时 `args` 就是 `["a", "b"]`。

> JDK 25 放宽了 main 的要求（JEP 512）：`main` 可以不是 `public`、可以不带 `String[] args`，甚至可以不是 `static`；还能不写类，直接写 `void main() { IO.println("Hello"); }`（「紧凑源文件」）。所以 `static void main()` 在 25 上也能跑，`javap` 会显示成 `static void main();`。这些是给初学者和脚本用的，**先别用**：JDK 21 及以前只认 `public static void main(String[] args)`，拿到 17 / 21 的环境（很多公司和笔试平台）直接报找不到 main 方法。面试手写代码和真实项目都用上面的标准写法，而且这种标准写法能帮你理解类、static、访问修饰符这些后面要学的概念。

### 常见报错对照

| 报错 | 原因 |
|---|---|
| `class L01_Hello is public, should be declared in a file named L01_Hello.java` | public 类名必须和文件名一致 |
| `错误: 找不到或无法加载主类 L01_Hello.class` | 运行时写成了 `java L01_Hello.class`，应写类名 |
| `错误: 找不到或无法加载主类 L01_Hello` | 类在包里，要写全名 `week01.L01_Hello`；或 `-cp` 指的目录不对 |
| `错误: 在类 week01.L01_Hello 中找不到 main 方法`（JDK 21 及以前） | main 没写成 `public static void main(String[] args)` |
| `javac: command not found` / `不是内部或外部命令` | PATH 没配好，或没新开终端 |
| `UnsupportedClassVersionError ... class file version 69.0 ... only recognizes up to 65.0` | 用高版本 JDK 编译，在低版本 JVM 上运行（69=25，65=21） |
| Windows 下中文输出乱码 / 编译报"编码 GBK 的不可映射字符" | `javac -encoding UTF-8 L01_Hello.java` |

## 六、面试常怎么问

这一项在面试里一般出现在 Java 基础的开头，问得不深，但答错很减分：

1. **JDK、JRE、JVM 的区别和关系？** → 包含关系 + 各自作用；加分：JDK 9 后不单独发 JRE、jlink。
2. **Java 为什么能跨平台？JVM 跨平台吗？** → 字节码平台无关，JVM 平台相关。
3. **Java 是编译型还是解释型语言？** → 编译与解释并存，讲清 javac + 解释器 + JIT 热点代码。
4. **什么是字节码？有什么好处？** → 一次编译到处运行；比纯解释执行快；JVM 还能对它做校验保证安全。
5. （偶尔）**Oracle JDK 和 OpenJDK 的区别？** → OpenJDK 是开源参考实现，Oracle JDK 基于它构建；JDK 11 之后功能几乎一致，主要差在授权和商用收费。

## 八、我的作答与纠正（2026-10-05）

### 自测题 1：只运行 jar 需要装什么？要用 jstack 又需要什么？

**我的回答：** 需要 JVM；要用 jstack 需要 JDK，因为需要对应的开发工具来看线程栈。

**批改：半对。**
- ✅ 后半句对：`jstack` 属于 JDK 自带的开发工具，只有运行环境是没有的。
- ❌ 前半句「只需要 JVM」不够。JVM 只负责执行字节码，程序用到的 `String`、`System.out` 都在**核心类库**里。所以运行程序至少要 **JRE = JVM + 核心类库**。
- ➕ 加分点：JDK 9 之后官方不再单独发布 JRE，实际做法是直接装 JDK，或者用 `jlink` 裁剪出一个精简的运行时。

**标准答法：** 只运行程序，至少需要 JRE（JVM + 核心类库），现在一般直接装 JDK 或用 jlink 定制运行时；要用 jstack 排查线程，必须装 JDK，因为 jstack 是 JDK 里的工具，JRE 里没有。

### 自测题 2：JDK 25 编译的 class 能在 JDK 21 上运行吗？反过来呢？

**我的回答：** 不能运行；可以运行；高版本能够兼容低版本。

**批改：对，原因可以说得更准。**
面试官想听的是 **class 文件版本号**：
- JDK 25 编译出的 class 主版本号是 **69**，JDK 21 的 JVM 最高只认 **65**，类加载时检查到版本号太高，就会报 `UnsupportedClassVersionError`。
- 反过来没问题：新版 JVM **向后兼容**旧版本的 class 文件。

**标准答法：** 不能。class 文件头里有主版本号（25 是 69，21 是 65），JVM 加载类时会检查它，遇到比自己高的版本就抛 `UnsupportedClassVersionError`。反过来可以，因为高版本 JVM 向后兼容低版本的 class 文件。

### 自测题 3：「Java 是解释执行的，所以一定比 C++ 慢」哪里不准确？

**我的回答：** Java 是一次编译到处执行，先把整体编译一遍，然后放在 JVM 解释执行。

**批改：漏了最关键的 JIT。**
「先编译成字节码，再由 JVM 解释执行」只是前半段。后半段是：
- JVM 运行时会统计代码的执行次数，找出被频繁执行的**热点代码**；
- 由 **JIT 即时编译器**把热点代码编译成本机机器码并缓存，之后直接执行机器码；
- JIT 还能利用运行时信息做优化（比如内联）。

所以 Java 是「**编译与解释并存**」，热点代码最终跑的也是机器码，「一定比 C++ 慢」不成立。真正的代价是**启动时需要预热**。

**标准答法：** 不准确。Java 先由 javac 编译成字节码，运行时解释器执行字节码，同时 JIT 把热点代码编译成本机机器码并做运行时优化，所以 Java 是编译与解释并存的。热点代码跑的也是机器码，稳定运行后的性能可以接近 C++，主要代价是启动时的预热。

### 附加题：Java 服务刚启动的前几分钟，接口为什么比运行一段时间后慢？

**我的回答：** 刚启动时还没有热点代码，所以每一次执行可能都要编译成机器码再执行；之后 JIT 发现热点代码，把这段代码的机器码缓存起来直接执行，就省去了编译的时间。

**批改：大方向对，但有个细节说反了。**
- ❌ 刚启动时**不是每次都编译成机器码**，而是**根本不编译**，由解释器逐条解释字节码，所以慢。
- JVM 统计方法调用次数和循环次数，超过阈值才认定为热点代码，交给 JIT 编译成机器码，之后直接跑机器码。
- 前期慢有两个原因：大部分代码还在解释执行；JIT 编译本身也要占用 CPU。
- ➕ 另一个原因：类是第一次用到时才加载的（第 18 周学 JVM 类加载时细讲）。

**标准答法：** 刚启动时字节码由解释器逐条执行，JIT 还没把热点代码编译成机器码，编译过程本身也占 CPU；加上类第一次使用时才加载，所以前期慢。运行一段时间后，热点代码已被 JIT 编译成优化后的机器码，速度就上来了。这就是 JVM 的「预热」问题。

### 延伸问题：C++ 快，是不是因为它完全编译成机器码再执行？

**我的想法：** C++ 快是不是因为它完全编译成机器码然后执行？

**解答：对了一半。**
「提前全部编译成机器码」（AOT）解释的是 **C++ 启动就快**：没有解释执行阶段，也不用预热。

但比**稳定运行后**的速度，这就不是主要原因了，因为那时 Java 的热点代码也已经是机器码。剩下的差距主要来自：

| 方面 | C++ | Java |
|---|---|---|
| 内存管理 | 对象可以分配在栈上，内存由程序员手动释放 | 对象基本都在堆上，靠 GC 回收；GC 占 CPU，有时还会暂停程序 |
| 内存布局 | 数据可以紧凑连续存放，CPU 缓存命中率高 | 每个对象都有对象头，数组里存的是引用，访问要多跳一次 |
| 运行时检查 | 不检查越界和空指针（快，但更容易出 bug） | 数组越界检查、null 检查都有开销 |

反过来，**JIT 也有 C++ 没有的优势**：它能看到程序实际怎么运行。比如某个接口在运行中只出现过一种实现，就能直接内联掉这次调用。所以有些场景下，Java 稳定运行后和 C++ 差不多，甚至更快。

**一句话总结：** C++ 快在启动快和能完全掌控内存；Java 慢在预热，以及 GC 和对象模型带来的开销，并不是一直在解释执行。GC 和对象布局在第 18 周学 JVM 时展开。

### 实操中发现的问题：main 方法写法

`javap` 显示 `static void main();`，说明写成了 `static void main()`，而不是标准的 `public static void main(String[] args)`。
- JDK 25 放宽了 main 的要求（JEP 512），所以能跑；
- JDK 21 及以前只认标准写法，很多公司项目和笔试平台还在用 17 或 21，会直接报「找不到 main 方法」；
- **以后统一用 `public static void main(String[] args)`。**
